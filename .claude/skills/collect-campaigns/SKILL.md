# collect-campaigns — 施策データの収集・メンテナンス

還元施策データ(data/campaigns.json)の新規収集と既存メンテを行い、**人間レビュー可能な下書き(working tree への編集+サマリー報告)まで**を作る。コミット・プッシュは絶対にしない(ユーザーのレビューと指示を待つ)。

必読の前提ドキュメント(実行のたびに参照):

- `docs/coupon-collection-tos.md` — 規約適合性の判断根拠と収集原則。**本スキルのガードレールの正本**
- `data/README.md` — スキーマ仕様・収録基準・運用ルール
- `.claude/skills/collect-campaigns/sources.md` — 情報源カタログ(入口 URL・アクセス方式・ソース別の読み方)
- `.claude/skills/collect-campaigns/mapping.md` — 事実 → campaigns.json への変換規則

## 引数

```
/collect-campaigns                          # フル実行(全ソースの新規収集+メンテ)
/collect-campaigns paypay|aupay|dpay|aeon|merpay|card|amex|municipal   # ソース限定
/collect-campaigns maintenance              # 既存データのメンテのみ
/collect-campaigns municipal 関東           # 自治体を地域ブロック限定で(北海道・東北/関東/中部/近畿/中国・四国/九州・沖縄)
/collect-campaigns rakuten: くら寿司 サンマルクカフェ   # ヒント(楽天ペイはこのヒントがある時だけ収集)
/collect-campaigns aupay: コジマ            # ヒントは全ソース共通の構文(指定チェーン起点で優先探索)
```

- `card` = 三井住友カード(半手動)+三菱UFJニコス
- `aeon` = AEON Pay(自治体クロスチェック+PR TIMES/加盟店側。イオン系ドメインには行かない。必要時のみ半手動。sources.md 参照)
- `merpay` = メルペイ(PR TIMES・加盟店側から収集。メルカリ側ドメインには行かない。sources.md 参照)
- **ヒント構文は全ソース共通**: `<ソース>: <チェーン名…>`(「今◯◯でやってるはず」等のユーザー持ち込み情報の正規の入口)。指定があると、そのソースの通常巡回に加えて指定チェーン起点の探索(sources.md「店舗限定・タイアップ型施策の発見(共通)」)を優先的に行う。ガードレールは通常どおり適用(禁止ドメインのヒントでも加盟店側・公式記事側から取る)
- 楽天ペイだけは **`rakuten:` ヒントが与えられた場合のみ**対象(ヒントが唯一の発見経路。自治体クロスチェックでの検出は除く。§ 自治体クロスチェック)
- 複数指定可(例: `/collect-campaigns paypay municipal 関東`)

## ガードレール(違反禁止。docs/coupon-collection-tos.md の共通原則を実行ルール化したもの)

1. **事実情報のみ収録する**。還元率・期間・上限・条件・対象店舗名・出典 URL を自前の文言で構造化する。各社ページの説明文のコピペ・画像の取り込みは禁止
2. **楽天グループのドメインにアクセスしない**(pay.rakuten.co.jp / checkout.rakuten.co.jp / corp.rakuten.co.jp 等すべて)。楽天ペイ施策の事実は加盟店・自治体側の公表からのみ取得する。**メルカリグループのドメインも同様に禁止**(mercari.com / jp.mercari.com / jp.merpay.com 等。メルペイ施策の事実は PR TIMES・加盟店・自治体側の公表からのみ取得する)
3. **三井住友カード(smbc-card.com)・イオン系ドメイン(aeon.co.jp / aeon.com 等)にツールでアクセスしない**。403 を UA 偽装や別クライアントへの切り替えで迂回しない。半手動フロー(sources.md 参照)を使う
4. **アプリ内限定情報・裏 API に手を出さない**。PayPay coupon-corner、au PAY / d払いのアプリ内クーポン、JS 描画一覧を支える API(docomo `/api/` 等)の直叩きは禁止
5. **フェッチ前に対象ドメインの robots.txt を確認**し(1 実行内でドメインごとに 1 回でよい)、Disallow パスはスキップする
6. **初出の民間ドメイン**(加盟店・キャンペーン実行委員会・特設サイト等)は robots.txt+サイト規約を確認し、結果で分岐する:
   - **問題なし**(自動アクセス禁止条項が無い) → 人間に確認を求めず**そのまま収集を続行**し、確認結果を docs/coupon-collection-tos.md「加盟店サイトの確認記録」への追記として下書きに含める
   - **問題あり・判断不能**(禁止条項がある、規約が見つからず判断に迷う、楽天グループ等の禁止ドメイン) → そのドメインからは収集せず、取れなかった事実を「要確認」としてレビューに回す(ユーザーの目視確認か内容貼り付けを依頼する)
7. **自治体・公的機関ドメイン**(lg.jp 等)は robots.txt 確認+利用規約が政府標準利用規約(CC BY 4.0 互換)系であることの確認でよい(個別記録は不要。標準系でない規約なら加盟店同様に記録)。商工会議所・実行委員会等の民間ドメインは加盟店扱い(規則 6)
8. **低頻度・少ページ**を守る。一覧+差分のある詳細ページのみ読む。同一ページの再取得を繰り返さない

## 実行フロー

### Phase 0 — 現状把握

1. `data/campaigns.json`・`data/merchants.json`・`data/payment_methods.json` を読む。**`qr_payments[].municipal_defaults`(自治体施策のサービス既定文言: `payment_instruction` / `ineligible_notes`)を決済サービスごとに控えておく**——自治体施策の照合・下書きはすべてこの既定との差分で判断するため(#89)
2. 今日の日付で各施策の状態を整理: ACTIVE / UPCOMING / 終了(30 日以内) / 終了(30 日超=削除候補)
3. 引数を解釈して対象ソース・地域ブロックを確定する

### Phase 1 — 既存メンテ(`maintenance` またはフル実行時)

各収録済み施策について:

1. `detail_url` をソース別アクセス方式(sources.md)に従って再確認する。SMCC 由来(および機械で読めない MUFG ページ)の URL はユーザーに **HTML 保存**を依頼し(手順は sources.md)、楽天ドメインの URL は内容貼り付けを依頼する。**リンク切れ(404 等)の扱い**: 期間終了済みの施策のリンク切れは**無視してよい**(終了後 30 日超で削除されるため直さない・報告しない)。**期間中の施策**(残り日数がわずかでも)のリンク切れは差し替え先を探し、見つからなければ「要確認」として必ず報告する
2. **改定検知**: 率・期間・上限・条件・**対象チャネル**(店頭/アプリ注文限定の別。mapping.md「対象チャネルの確定」)が公表と食い違えば修正下書きを作る。自治体施策は施策直下(全サービス共通)を 1 箇所直せば全 variant に効く
3. **自治体施策のサービス既定との突き合わせ**(#89): 各 variant について、公式の対象決済・対象外機能を **Phase 0 で控えた `municipal_defaults` と比較**する。(a) 公式が既定と同じ → variant に `payment_instruction` を書かない(書いてあれば削除の下書き)、(b) 公式が既定と違う(対象決済が広い/狭い、サービス固有機能の除外が追加) → variant の `payment_instruction` 上書き・`ineligible_notes` 差分行を下書き、(c) **既定側の文言そのものが公式と食い違う施策が出た**(例: PayPay が他社クレジットカードを対象にした自治体施策) → その施策は variant で上書きしつつ、既定の見直し候補として「要確認」に挙げる(既定を変えるならそのサービスの自治体施策を全件再確認してから。mapping.md「自治体施策の payment_variants」)。既定注記が施策に付くことは施策側の JSON を見ても分からないため、**展開後の表示文言(既定込み)で公式と照合する**こと
4. **早期終了検知**: 予算到達・早期終了の告知があれば `period_end` 修正または削除提案
5. 確認できた施策の `verified_date` を実行日に更新する(確認できなかったものは据え置き、理由を報告)
6. **終了後 30 日超**の施策は削除の下書きを作る(data/README.md「期限切れデータ」ルール)

### Phase 2 — 新規収集

sources.md のソースごとの手順で入口を巡回し、未収録の施策候補を集める。候補ごとに記録するもの: 施策名(自前要約)・事実(率/額・期間・上限・条件・対象チェーン/自治体)・出典 URL・取得日。

自治体施策は必ず § 自治体クロスチェック を通す。

### Phase 3 — フィルタと下書き

1. **収録基準**(data/README.md): 還元率 5% 以上(自治体・カード会社期間限定)。クーポンは割引率 5% 以上 OR 割引額 100 円以上 AND 全員配布 AND 主要チェーン対象。**「主要チェーン対象」は特定複数店舗限定でも、公式が対象店舗を言い切る網羅リストがあれば満たす**(`official_store_list.list_is_exhaustive: true` 付きで収録。mapping.md 参照。コジマ×ビックカメラ型を基準解釈で見送らない)。**常設 `card_program` は別基準: 実効 2% 以上の merchant のみ収録**(実効=最有利カードクラス・1pt=1円換算の絶対%。提示分は決済分と分離して起こし、カード現物提示型は `presentation_only: true`+`card_id` で(#80)、ポイントプログラム会員提示型は `presentation_only: true`+`point_program_id` で収録(#39)。閾値 2% は提示施策にも適用(全加盟店共通の通常提示 1% は収録しない)。詳細は data/README.md「常設 card_program の収録基準」と mapping.md「提示と決済の分離」。#58)
2. 基準内 → mapping.md の変換規則で `data/campaigns.json` に追記する(working tree に直接編集。git diff がレビュー画面になる)。`updated_at` も更新する
3. 対象チェーンが merchants.json に無い場合は merchant エントリの下書きも作る(`reading`・`aliases` 必須。`category`・`yolp_search` は判断根拠が無ければ要確認マークを付けて報告)
4. 基準外・収録不能 → **見送り一覧**へ(理由付き: 基準未満/ネット限定/会員限定・要ログイン/アプリ内限定/断定不能 等)。ネット限定施策(d曜日等)は現時点ではスキーマに区別が無いため一律見送り
5. 抽選型は `lottery`(rate_base/discount_amount とも null)、定例日型は `recurrence`、自治体は原則 `may_end_early: true`、複数率は `rate_rules`+最大値を `rate_base`、など mapping.md の規則に厳密に従う

### Phase 4 — 検証と報告

1. `./gradlew :app:testDebugUnitTest` を実行し整合性テスト(参照切れ・フィールド排他・rate_base=rate_rules 最大値・記述形の規約=municipal は `payment_variants`・`operator` 省略・明示 null 不在)を通す。失敗したら**下書き(データ)側を直して**再実行
   - **テストやアプリコードの修正が必要になる下書きは登録しない**(このスキルの変更対象は data/ とドキュメントのみ)。該当分は下書きから外し、「既存テストの不変条件と衝突する(例: external な promotion)」等の理由付きで要確認に回す。コード側を直すかはユーザーが別途判断する
2. サマリー報告を出す(§ 報告フォーマット)
3. **コミットしない**。レビュー後の指示を待つ

## 自治体クロスチェック

自治体施策を 1 件見つけたら(どの決済手段の入口経由でも):

1. 自治体公式ページを探す(Web 検索: 「{自治体名} キャッシュレス キャンペーン {年}」等。lg.jp / 自治体公式ドメインを優先)
2. 公式ページで **対象決済手段の全リスト** と率・期間・上限を確認する(一次情報として決済会社ページより優先)
3. **キャンペーンにつき 1 エントリ**(id `{自治体}_{YYYY_MM}`。例: 湯沢市 = `yuzawa_2026_07`)を作り、対象決済手段のうち payment_methods.json の `qr_payments` にあるもの**それぞれ**を `payment_variants` の 1 要素にする(#89。mapping.md「自治体施策の payment_variants」)。率・期間・上限・自治体が決める対象外は施策直下に 1 度だけ書く。**楽天ペイもここで収録できる**(自治体側情報源なので楽天規約の射程外。ガードレール 2 は維持=楽天ドメインには行かない)
4. variant ごとに、決済会社側ページ(または自治体ページの当該サービス欄)の対象決済・対象外機能を **`municipal_defaults` と比較**し、同じなら `payment_instruction` を書かず、違うときだけ上書き・差分行を書く(Phase 1 手順 3 と同じ規則)。`detail_url`(必須)は決済手段ごとの案内ページがあればそれ、無ければ自治体公式ページ。`verified_date`(必須)はサービスごとに確認した日
5. 率・上限がサービスで違う場合は variant にまとめず**別施策**にする(variant は共通項を上書きできない)
6. 自治体公式ページが見つからない・対象決済手段が読み取れない場合は、確認できた決済手段のみ収録し、他は断定せず「要確認」として報告する(不確かな情報で好条件を提示しない方針)
