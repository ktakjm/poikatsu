# issue #13 期待価値スコア比較 設計書

作成日: 2026-08-19 / 対象: [issue #13](https://github.com/ktakjm/poikatsu/issues/13)(Phase 3: 最適化アドバイス)

判定エンジンを「還元率比較」から「期待価値スコア比較」へ拡張する。スコアの正体は**円換算の実質還元率(%)**であり、抽象的な点数は導入しない。

## 1. スコープ

### やること(5 サブ機能)

1. **1pt 価値モデルの通貨単位への一般化** — J-POINT のカード単位 `point_value` を point_currencies へ移設し、全通貨でユーザーが 1pt=何円かを設定できるようにする
2. **期間限定ポイント残高・失効日の手入力** — 通貨ごとに 1 件(直近失効分)
3. **期待価値スコアによる最良判定** — 実質% = 名目還元率 × 通貨価値係数。消化ボーナスは優先ルールとして実装
4. **提示スタック合算** — 決済分 + 提示分の「実質○%相当」表示(二重取りまで)
5. **rebate vs coupon 損益分岐** — 分岐額の自動表示のみ(購入額入力なし)

### 見送り(2026-08-19 決定・理由つき)

| 論点 | 判断 | 理由 |
|---|---|---|
| lottery(抽選型)の期待値換算 | 見送り | 当選確率・最大額が現状 memo の文章のみで、構造化のスキーマ拡張+データ収録コストが大きい。スコア基盤とは独立に後付け可能 |
| QR 決済のユーザー実効率(PayPayステップ等) | 見送り | 収録基準「差 5% 未満は割り切り」(schema-refresh-plan §2.2)が生きている。必要になれば設定画面にカードの effective_rate 相当を足すだけで後付け可能 |
| 三重取り(チャージ元カード)のモデル化 | 見送り | チャージ経路のモデルが丸ごと新規になる。合算は決済 1 + 提示 N の二重取りまで |

いずれもスコア層の設計を変えずに後付けできることを設計条件とする。

## 2. アーキテクチャ: スコア層の新設(案B)

`domain/ExpectedValueScoring.kt`(純 Kotlin)を新設する。

```
JudgmentEngine(率の解決・名目率)
        │ JudgmentResult(名目率のまま)
        ▼
ExpectedValueScoring(円価値換算に一本化)
  - 実質% = 名目率 × 通貨価値係数(1pt価値 × 条件付き倍率)
  - 失効間近ポイントの通知判定(施策とは独立)
  - 提示スタック合算
  - 損益分岐額
        │
        ▼
determineBest は実質%の最大で選ぶ
```

- **円価値換算はスコア層に一本化**する。既存のウエル活倍率適用(`boostedCampaignRate`)はスコア層へ吸収し、`usesCardRate` 型の二重適用問題(マージ層とエンジン層で同じ係数を掛ける事故)を構造的に防ぐ。
- 通貨が特定できない決済手段(例: 三菱UFJカード=point_currency_id なし)は係数 1(等価)で従来どおり比較する。
- 「今日」の日付は domain へ引数で渡す(純 Kotlin 維持・テスト容易性)。
- discount(定額割引)・lottery・提示のみ施策の最良判定からの除外は現行踏襲。

## 3. ポイント価値モデル(payment_methods.json schema_version 10)

- `point_currencies[]` を 1pt 価値の持ち主にする:
  - 通貨 `j_point` を新設し、`jcb_original` に `point_currency_id: "j_point"` を張る
  - カード単位の暫定 `point_value`(`PointValueConfig`)は**通貨側へ移設して廃止**。label/note は J-POINT のように説明が要る通貨だけ持つ
- **全通貨がユーザー設定可能な 1pt 価値(円)を持つ**。既定値 1.0 円
- `point_multiplier`(ウエル活 ×1.5)は「条件付き増価」として現行のまま共存:
  - `実効価値係数 = 1pt価値 × (倍率ON ? factor : 1)`
- プリセット(使わない=0円 / 等価=1円 / カスタム)は**アプリ UI 側の定数**とし JSON には持たせない(データは汎用に保つ方針)。「貯まるが使わない」層は 0 円プリセットで実質 0% になる(名目率との乖離は仕様)

スキーマ変更に伴い data/README.md と code-guide §3 の ER 図を更新する(Stage 1)。

## 4. 消化ボーナス = キャンペーン有無によらない失効通知

issue の式 `スコア = 還元率 × ポイント価値係数 + 消化ボーナス` の第 2 項は、スコアへの加点や最良判定の入れ替えではなく、**施策と独立した失効通知**として実装する(2026-08-19 ユーザー決定)。

**理由**: 施策を開催しているお店でポイント払いすると「ポイント消化でも施策対象になるか」の確認が必要になり、むしろ**施策の無いお店で消化したい**のが実態。したがって消化アドバイスを判定(=施策のあるお店)に紐付けず、施策の有無・決済手段の有無によらず通知する。当初案の「QR の point_currency_id 一致で最良判定を持ち上げる優先ルール」は廃止。

- **表示**: 判定結果画面に「残り3日で失効する楽天ポイント 500pt あり」のような注記を、そのお店の施策有無・お支払い方法によらず出す。複数通貨が該当するときは失効日が近い順に列挙
- **しきい値**: 失効まで 30 日以内(定数 `EXPIRY_NOTICE_DAYS = 30`)で表示し、7 日以内(定数 `EXPIRY_WARN_DAYS = 7`)は warning 系ロールで強調
- **失効日を過ぎた入力は非表示**にし、設定画面の該当行に「失効済み」を警告表示して入れ直しを促す
- 通知の判定に必要な入力はユーザーの残高・失効日と「今日」のみで、施策データに依存しない(スコア層の純関数として最も単純な形になる)

## 5. 提示スタック合算

- 最良の決済手段が決まった後、その店で併用可能な提示施策(`presentationJudgments`: プログラム会員提示・カード現物提示)の実質%を円換算で合算:
  - `合算実質% = 決済の実質% + Σ 提示の実質%`(各項に各通貨の価値係数を適用)
- 通貨をまたぐ足し算は 1pt 価値のユーザー設定値で換算することで正当化する(1pt=1円の暗黙仮定を置かない)
- 表示: 判定結果ヘッダに「**実質○%相当**(決済 7% + 提示 3%)」。既存の「あわせて提示でおトク」並記枠は内訳の説明役としてそのまま残す
- 会員未登録プログラムの提示分は従来どおり枠にも合算にも入れない

## 6. rebate vs coupon 損益分岐

- 各 discount 判定カードに分岐額を注記:
  - `分岐額 = 割引額 ÷ (最良の実質% / 100)` を 10 円単位で切り上げ。ここでの実質%は**決済分のみ**(提示分は割引を使う場合でも併用でき両辺に等しく乗るため、比較から除外)
  - UI 文言例: 「2,000円未満のお買い物ならこちらが得」
- 最良の rebate が無い店(実質 0%)では「金額によらずこちらが得」
- 最良判定の枠組みは変えず discount は別枠のまま。購入額入力 UI は作らない

## 7. UI 表示

- スコアの表示は「実質○%相当」。名目と実質が異なるときだけ併記(例: 7%(実質10.5%相当))。等価(1円)設定で倍率も効かない通貨は従来表示のまま
- 失効間近ポイントの通知は判定結果画面の上部に注記行として表示(7 日以内は warning 系で強調)。最良判定カードの表示には影響させない
- UI 文言は「キャンペーン」「お店」「お支払い方法」の表記統一に従う。文末疑問符は全角？

## 8. 設定 UI・DataStore・バックアップ

- 設定「ポイント」セクション(PaymentMethodsSettings.kt)の各通貨行を拡張:
  - **1pt の価値**: タップでピッカー(プリセット「使わない(0円)」「等価(1円)」+カスタム値。既存 `PointValuePickerDialog` を通貨単位に一般化)
  - **期間限定ポイント**: 残高(pt)+失効日(通貨ごとに 1 件)。日付は M3 DatePicker(横画面は Input モードで開く既存ルール適用)。失効済みは行に警告表示(warning 系ロール)
- DataStore 新キー:
  - `POINT_CURRENCY_VALUES: Map<通貨id, Double>`(1pt 価値円)
  - `POINT_BALANCES: Map<通貨id, {残高pt, 失効日}>`
- **マイグレーション**: 既存 `CardOverride.pointValue`(jcb のみ)は初回読み込み時に `j_point` の `POINT_CURRENCY_VALUES` へ変換して廃止
- バックアップ `SettingsBackup` は schemaVersion 3 へ。v2 読み込み時は jcb の pointValue を j_point へ変換する後方互換を維持

## 10. テスト方針

既存規約(code-guide §8)の 3 層で書く:

1. **Kotlin フィクスチャ**: スコア層の純関数(実質%換算・失効通知のしきい値・合算・分岐額・丸め)を網羅。日付は固定値を渡す
2. **実データ**(`実データ_` プレフィックス): data/*.json で通貨参照・ウエル活のスコア反映を検証
3. **data-test ショーケース**: `test_point` に残高・失効・1pt 価値のショーケースを追加し、TestDataIntegrityTest で担保
